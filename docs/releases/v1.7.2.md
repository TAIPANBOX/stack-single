# stack-single 1.7.2

The browser runs under an AppArmor profile of the stack's own, so a Debian 13 box no longer runs it unconfined. The fire drills for the MCP broker are on the box, with a key of the broker's own, and a person runs them with one command. TokenFuse 1.24.0 shows an agent only the MCP tools its policy does not refuse outright.

## Upgrade first

1. **The tokenfuse services are recreated with 1.24.0**: `tokenfuse-gateway`, `tokenfuse-mcp-broker`, `tokenfuse-cloud`, and `tokenfuse-gateway-openai` on a box with the OpenAI door. On a Compose below 2.35 a recreated gateway takes its dependents with it; calls through a door stop while they restart. No migration and no new setting. The broker's `tools/list` now leaves out the tools wardryx refuses the calling agent outright (a `deny_tool` rule, or outside an `allow_tool` list); a tool with no grant stays listed, so its call is still held for a person. A client that counted on the upstream's whole listing sees fewer tools.
2. **The broker's key list gains one entry, and its static list one id.** `drills-broker`, the fire drills' key at the broker, is appended to `TOKENFUSE_MCP_KEYS` (every earlier entry stays byte for byte, and the line keeps the form it had) and named on `TOKENFUSE_MCP_AGENT_TOKENS_STATIC_KEYS`; the same secret is written to `drills/broker.key` (uid 65532, mode 0400). The broker is recreated with them. The key is never printed, and a re-run keeps it.
3. **On a host where the installer can load the stack's AppArmor profile, `.env` moves from `unconfined` to `scopyx-browser`** (`SCOPYX_BROWSER_APPARMOR`). The profile is Docker's default plus the one rule Chrome's sandbox needs (`userns,`), loaded with `apparmor_parser -r` and kept in `/etc/apparmor.d`. A box that runs the browser recreates `scopyx-browser` under it; a box without the `egress` or `browser` profile writes the line and recreates nothing for it. `status` names the profile the running browser is under, and is a FAIL for `unconfined` where the host could have confined it.
4. **The installer checks the signature of the drills' image and pulls it** (mockryx v0.5.0), so `docker compose run --rm mockryx-drill` starts an image the install verified. Nothing starts it.
5. **Going back to 1.7.1 needs nothing special.** The rollback index stays 1. 1.7.1 leaves `drills-broker` in the broker's key list and static list, which it does not use, and writes `unconfined` back only if its throwaway asks for it.

## What is new

- **The fire drills for the MCP broker** (#179, CLAUDE.md invariant 74). `docker compose run --rm mockryx-drill` sends this box's broker three hostile tool calls: a raw secret in the arguments, personal data in the arguments, and a call to a tool nothing grants, which the tool hold must keep for a person. The service sits behind the `manual` profile, which no install passes. It presents `drills-broker`, a key of the broker's own and never the gateway's, from `drills/broker.key`. mockryx's own tool-hold drill asks an MCP server for an answer this box has no server to give, so the box mounts its own copy over it (`drill-scenarios/mcp-ungranted-tool-held.yaml`): its first call is held for a person as before, and its second, from a drill identity, gets past the hold and is refused by the broker's vault, because the secret handle it carries is scoped to other tools; nothing reaches a server. A run leaves one pending approval on wardryx for an id under `ungranted.invalid`; nobody needs to answer it, and later runs reuse it. The broker runs only with `WITH_TYPED`, `WITH_EGRESS` or `WITH_BROWSER`; without it the drill stops with exit 2.
- **The browser's AppArmor profile** (#178, CLAUDE.md invariant 73). See Upgrade, item 3.
- **TokenFuse 1.24.0** (estate-gates GAPS G3.13). See Upgrade, item 1.

## Fixed

- **A rewritten broker key line no longer breaks the installer's own broker check** (#179). Written back in quotes, the line made the check, and CI, read the broker's first key with a quote in front of it, and the broker refused it 401. The line now keeps the form it had, and both readers take either form.
