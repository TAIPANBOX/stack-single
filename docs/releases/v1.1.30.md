# stack-single 1.1.30

Wardryx moves to `v1.3.0`, the policy decision point. A policy can now name the
only tools its agents may use, and `deny_tool` also refuses a tool that a request
names only in its tool call. Nothing else moves.

## What moves

- **Wardryx `v1.2.0` -> `v1.3.0`**: the policy plane (`WARDRYX_IMAGE`, the
  `wardryx` service in `compose.yaml`, and `components.json`). Release notes:
  [wardryx v1.3.0](https://github.com/TAIPANBOX/wardryx/releases/tag/v1.3.0).
  - **`allow_tool`**: a policy may carry a list of tool names, the only tools its
    agents may use. A tool the list does not name is denied, and no approval
    lifts that denial. An empty or absent list restricts nothing.
  - **`deny_tool` reads the tool call's name.** A request that names a denied
    tool only in its `tool_call` (the MCP broker's field) is now refused. Before
    this release a benign tool list let it through.
  - **Caching.** A decision under `allow_tool`, and under `deny_tool` for a
    request that carries a tool call, is not cacheable. Such a policy costs one
    policy round trip per call.

No other pin moves. TokenFuse stays at `v1.11.0`.

## Upgrading

- **Nothing to configure.** This release adds no environment variable and no
  route.
- **Nothing changes for a policy that does not use `allow_tool`.** A policy
  without the field keeps its policy version and decides as before.
- **The starter policy.** On its first run `install.sh` writes one `policy.yaml`:
  a human-approval rule above one dollar, and `deny_tool: [shell_exec]`, both for
  `agent://mockryx.local/*`. It sets no `allow_tool`, so the new list changes
  nothing on a fresh box. The `deny_tool` rule does now read the tool call's
  name, so a call named `shell_exec` is refused even where its tool list is
  benign.
- **Rollback trap.** A policy stored through `PUT /v1/policies/{id}` with
  `allow_tool` is silently stripped by an older Wardryx, which then allows every
  tool. A policy file with the field makes an older build refuse to start, which
  is loud. Before pinning back to `v1.2.0`, remove `allow_tool` from every stored
  policy.

## Not proven

- **A live run of this launcher on v1.3.0.** No stack was brought up with this
  pin here. CI runs the gates and the three install legs (default, delegation
  and typed-risk) on the pull request, which install the stack on Ubuntu with
  these pins. They do not show a live policy with `allow_tool` refusing a call.
- **The typed-risk path under `allow_tool`.** The MCP broker asks Wardryx only
  with `TYPED_RISK_SIGNAL=1`, and that path was not run against this build.
- **Whether the gateway's own decision calls carry a `tool_call`,** and whether a
  cache keyed on agent and tool set alone can serve a stale allow. A request with
  no tool call under `deny_tool` stays cacheable, so a caller must key on whether a
  tool call is present. Neither was checked against TokenFuse here.
- **The rollback path on this launcher.** The stored-policy trap above is stated
  from the Wardryx notes, not run on a stack.
