# stack-single 1.7.0

An agent's tool call that nothing grants now waits for a person, and a box with a history is told what that would stop before anything on it changes. This release also compares what Docker runs with the pins, keeps a journal on the box with a rollback index, and gives every container the same baseline, or a named reason why not.

Read this before you run the installer. A first run can stop, on purpose, and it recreates most of the stack once.

## Upgrade first

1. **On a box with a history, the run may stop with a table, and it changes nothing.** A box with no `policy.yaml` is new, and this does not apply to it. On any other box, before a package, a file or a container changes, the installer pulls the pinned wardryx image if the box does not have it, its signature checked first, and asks `wardryx replay -policy <what this run would write> -format json` about the box's own decisions, with what wardryx's store holds added.

   A box where no call of an agent outside the seeds would wait for a person goes straight on, and that includes every box that never ran the MCP broker: no tool call has reached wardryx there. Otherwise the run stops, exit 1:

   ```
      With the tool hold on, these calls would wait for a person (0 of 2 decisions could not be asked):

      CALLS   LAST SEEN             TOOL                      AGENT
      1       2026-11-07T16:27:56Z  ask                       agent://lab.example/tool-user

      To give each agent what it needs, move the box first, with the hold off, then grant, then turn it on:

        TOOL_HOLD=0 ./install.sh
        ./install.sh agent-allow 'agent://lab.example/tool-user' 'ask' --why 'what it is for'
        TOOL_HOLD=1 ./install.sh
   ```

   No file changes, no container is touched, the journal gets no line, and the image goes again if this run pulled it. A history that could not be asked stops the run the same way, and says how much of it, because a list of nothing over decisions nobody could read says nothing. So does a box that cannot reach ghcr.io for the image, and a replay that gives no report.

   The three commands, in this order:

   - **`TOOL_HOLD=0 ./install.sh`** moves the box to this release with the hold off, and `.env` keeps the choice. It comes first because a wardryx older than 2.6.0 refuses `grant_tool` on `PUT`, so no grant can be written before the move. If you want the hold off, this one line is all you run.
   - **`./install.sh agent-allow <agent> <tool[,tool]|all> --why 'what it is for'`**, once per agent. It takes effect at once with no restart. It asks for an agent token: an agent that calls with a static key adds `--static-key`, or its calls are refused, model calls included. With the hold off, `./install.sh agent-list` asks the question again and shows what would still wait.
   - **`TOOL_HOLD=1 ./install.sh`** writes the block and restarts wardryx. Said in the environment, it goes on over whatever is still on the list and shows it: those agents wait for a person until something grants their tool. A `TOOL_HOLD=1` line in `.env` does not do this, so a line left in a file cannot answer for you.

   A printed command names only text a shell reads nothing in. A recorded id that a shell would run, or one with no `agent://`, stays in the table with no command, and the run counts those rows.

2. **Most of the stack is recreated, once.** Every service but `init-volumes`, `keyryx` and `vouchryx` took the baseline, so each one that runs is recreated on the first run. On a default box going from 1.6.4 on Compose 2.26.1 that was 13 containers: `agent-conform`, `caddy`, `console`, `heraldyx`, `idryx`, `keyryx-witness`, `policy-db`, `record-seal`, `tokenfuse-cloud`, `tokenfuse-gateway`, `verdryx-slo`, `wardryx` and `wg`. A second run recreated none. Whatever else your box runs from a profile is recreated with them. Calls through a door stop while it restarts, and so does a session over the tunnel. A device issued before keeps working.

   On a Compose below 2.35 a recreated service takes what sits below it: `policy-db` takes `wardryx`, `wardryx` and `tokenfuse-cloud` take `tokenfuse-gateway` and `console`, and `console` takes `caddy`. None of that reaches `keyryx` or `vouchryx`. Their blocks and `init-volumes` are line for line what 1.6.4 had, so this release spends no certified key: custody held the same count before and after the upgrade on that Compose.

3. **A service under your own `compose.override.yaml` can now fail with `Read-only file system`.** Every service has a read-only root except the ones `hardening-exceptions.json` names, and your override can hold a mount or a port the baseline does not know about. A service that writes outside its volumes and its `tmpfs` gets that error. Give the path a volume or a `tmpfs` in your override. `read_only: false` there lets it run, and the drift check then prints a `FAIL` line for it, so every install ends with a failed check and the journal's floor does not move.

4. **`policy-db` now starts as uid 70**, the image's own postgres user, with no root step. A volume the image's entrypoint set up is already uid 70, and there is nothing to do. A `pgdata` you restored or copied by hand may not be, and then postgres stops with `Permission denied` and wardryx waits for it. Check first, and the first number must be 70:

   ```sh
   docker run --rm -v agent-stack_pgdata:/v busybox:1.36 stat -c '%u:%g' /v/pgdata
   docker run --rm -v agent-stack_pgdata:/v busybox:1.36 chown -R 70:70 /v/pgdata    # only if it is not
   ```

5. **If you run `scopyx-browser`, AppArmor decides whether Chrome's sandbox starts,** and the two hosts this installer supports disagree, so `compose.yaml` sets nothing. Each was measured with the whole baseline on:

   | Host | Docker's default profile | `apparmor=unconfined` |
   |---|---|---|
   | Ubuntu 24.04, Docker 28.0.4 | renders a page | `No usable sandbox`, because `kernel.apparmor_restrict_unprivileged_userns` is 1 |
   | Debian 13, Docker 26.1.5 | `credentials.cc`, `Permission denied`, with or without this baseline | renders a page |

   A browser that cannot start its sandbox answers `browse` with that error and fetches nothing. On a box like the second row, `apparmor=unconfined` for this one service in your `compose.override.yaml` is the line that works, and it is a wider door, so it is your decision.

6. **Four images move, by tag and digest:**

   | Image | 1.6.4 | 1.7.0 |
   |---|---|---|
   | wardryx | v2.5.1 | v2.6.0 |
   | tokenfuse (the gateway, the OpenAI door, the MCP broker, the FOCUS export) | v1.22.0 | v1.23.0 |
   | tokenfuse-control-plane | v1.22.0 | v1.23.0 |
   | genaryx-console (the console and the quality routines) | v1.8.4 | v1.8.6 |

   Two things tokenfuse 1.23.0 changes that a box can see. A held call's `-32004` now reads `requires approval (approval <id>) (<reason>)`, so a client that matched the old text exactly must match the new one. And its injection detector fires on Unicode tag characters and bidi isolates, and the firewall here runs in enforce unless you moved it, so a run that reads a page hiding text that way can lose tools it had before.

   A `*_IMAGE` line in `.env` keeps its image, and the drift check names it. A `WARDRYX_IMAGE` older than 2.6.0 cannot load the block: the run stops before `up` with `policy.yaml` as it was, and says what wardryx said. Move the line, or set `TOOL_HOLD=0`.

7. **wardryx changes its schema at its first start.** There is no step to take. `approvals` gains a nullable column, `pending_key`, and two partial indexes, and the start applies them the way it applies the rest of the schema. Writes to `approvals` wait for that build the first time. Rows that are already there have no key, so nothing can conflict.

## Rollback

**`TOOL_HOLD=0` first, then the older tree.**

```sh
TOOL_HOLD=0 ./install.sh          # from this tree: takes the block out, and restarts wardryx
cd /path/to/v1.6.4 && ./install.sh
```

A wardryx older than 2.6.0 refuses `when_no_grant` and `grant_tool` at load. In the other order it restarts in a loop, and because both doors and the broker fail closed, every call is refused, model calls included. `TOOL_HOLD=0 ./install.sh` from this tree puts that right.

The block is the installer's, so `TOOL_HOLD=0` takes it out. A `grant_tool` you wrote yourself outside the markers has to go by hand first. Grants written with `agent-allow` can stay in the store, where 2.5.1 reads past the key, and they are there again if you come back. The `pending_key` column and its indexes can stay too: 2.5.1 neither reads nor writes them.

What the journal says about it. This is the first release with a journal, and the first run on an existing box starts it with a `first-seen` line. `TOOL_HOLD=0 ./install.sh` writes its own `attempt` and `good` lines. 1.6.4 has no journal, so it reads no floor and leaves no line: the newest line stays that `good` of 1.7.0, whatever the box runs after it. The rollback index stays 1 in this release, because no older tree became unsafe: the wrong order is loud and refuses, and with the hold out 1.6.4 ran with every check passed. So no tree is refused, `ALLOW_ROLLBACK` has nothing to do here, and running 1.7.0 again later goes through.

`init-volumes`, `keyryx` and `vouchryx` are the same lines in both trees, so going back spends no certified key either.

## What is new

- **The tool hold.** On a new box a tool call through the MCP broker that nothing grants is held for a person: the agent gets `-32004` with the reason, and the console shows the hold. Model calls pass, and so do scopyx's questions about a fetch. A rule that only restricts an agent ends nothing, and only a grant lifts the hold. It is one block in `policy.yaml` between marker lines the installer alone writes, and every other line stays yours. Its seeds are the fire drills (`grant-drills`), the installer's own check (`grant-install-check`), and the operator agent's `fetch_url` and `browse` (`grant-operator-web`) when the run names `WITH_EGRESS` or `WITH_BROWSER`, or a scopyx of this box runs, on a box with agent tokens on. wardryx keeps one row per agent, run and call, and at most 20 waiting per agent. An install and `status` read what wardryx loaded off the bus, so a file that says on is not simply believed. `TOOL_HOLD=0` removes it all and `.env` keeps the choice.
- **`agent-allow`, `agent-deny`, `agent-list`.** `./install.sh agent-allow <agent> <tool[,tool]|all> --why 'text'` gives an agent a tool from the box, through `PUT /v1/policies`, with the admin key on standard input and never on a command line. It is in force with no restart, it is on the record as `policy_updated`, and the date and the reason go in the policy's name. `all` prints a warning. `agent-deny` takes a tool back, and the agent's next call waits for a person again. `agent-list` shows whether the hold is on and every grant with where it lives, and, with the hold off, what it would stop. Run them as root, because `.env` is 0600.
- **The console shows a person's grant as a token, once.** It is good for that one call, and whoever runs the agent sends it with the retry as `x-fuse-approval-token`. For anything that will come again, the answer is a grant.
- **A drift check.** `status`, and the end of every install, compare what Docker really runs with the pin in `compose.yaml`, one line per container, and they read the image Docker holds, not the name the container was given. An image that is not the pin, a tag with no digest, a stopped service, or a container compose does not know about is a `FAIL`, and on an install that is a failed check. An image set in `.env` or `compose.override.yaml` is a `note`. `status` now ends 0, 1, or 2 when it could not measure. It only reads, and it says what it is: root on the box can change either side.
- **An install journal and a rollback index.** Each run appends to `$STACK_DIR/.install-history`, root's, 0640: when, the tree's version and commit, its index and how it ended. The floor of a box is the highest index of a run with no failed check. A tree below the floor is refused in the preflight, with the way through: `ALLOW_ROLLBACK=1 ROLLBACK_REASON='why' ./install.sh`, and the reason goes in the journal. A piped install refuses a `compose.yaml` of another version before it replaces the box's file. `status` prints one line from the journal. This is a guard against mistakes and not against an attacker: the check lives inside the tree it checks, and root can edit the journal.
- **A baseline on every container.** `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, a `pids_limit` of its own and no core dump, on every service, and a user that is not root. `hardening-exceptions.json` names each thing a service does not take, with the reason and what closes it, and a gate fails on a service with neither. `init-volumes`, `keyryx` and `vouchryx` stay as they were until G3.11. The browser has `init: true`, 512 MiB of `/dev/shm` and a 2 GiB memory limit. There is no default memory limit for the rest. `focus-export` can start now: the image's entrypoint took its script as arguments, so it never had.
