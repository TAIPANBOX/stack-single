# stack-single 1.1.31

Personal data in prompts and tool arguments is now recorded in shadow on every
box: the gateway and the MCP broker read one PII switch, and it defaults to
shadow. Shadow refuses nothing and changes nothing that is forwarded. The stack
also seeds one allow-list rehearsal policy for Wardryx v1.3.0.

## What moves

- **PII detection in shadow, on the gateway and on the MCP broker.**
  `@decided 2026-10-13`, paraphrased: the launchers run TokenFuse's PII scanners
  in shadow by default, and an operator keeps one switch to move them. Compose
  sets `TOKENFUSE_DLP_PII` on `tokenfuse-gateway` and `TOKENFUSE_MCP_DLP_PII` on
  `tokenfuse-mcp-broker` from `${TOKENFUSE_DLP_PII:-shadow}`, so the two cannot
  disagree.
- **One switch, validated.** `TOKENFUSE_DLP_PII` takes `off`, `shadow`, `mask` or
  `block`. `install.sh` (section 0e) refuses any other value before it installs
  anything, and refuses a bad value already in `.env`. TokenFuse reads an unknown
  value as off without a word, so a misspelling would switch detection off on a
  box that looked covered.
- **Seeded policy, fresh installs only.** The `policy.yaml` that `install.sh`
  writes on a first run gains `mockryx-allow-list`: target
  `agent://mockryx.local/allow-list-rehearsal`, with `allow_tool` naming one tool,
  `lookup_order_status`. It is the rehearsal identity for the allow-list drill.
  Wardryx `v1.3.0`, already pinned, reads `allow_tool`; no pin moves.
- **Gate.** `scripts/pii-is-shadow.sh` (invariant 28), wired into CI, the
  pre-push hook and CLAUDE.md, with 18 teeth cases.

## What shadow does, and does not do

Shadow records and forwards. Nothing is refused, masked or rewritten:

- **Gateway.** The prompt goes to the provider unchanged, as it does today. The
  response carries an `x-fuse-dlp` header with the kinds found and a count, never
  the values. Nothing is logged for it.
- **Broker.** A tool argument with personal data is logged as a warning and
  forwarded unchanged. A tool response is logged the same way and annotated
  `_tokenfuse.dlp_pii`, then forwarded unchanged.
- A finding is a header or a log line. It is not an event on the bus, and it
  adds no row to the NDJSON streams.

## Upgrading

- **Nothing to configure for the default.** An existing box picks up shadow the
  next time `docker compose up -d` recreates the gateway, and the broker when the
  typed profile next starts it. What is forwarded does not change.
- **Back to off.** Put `TOKENFUSE_DLP_PII=off` in `$STACK_DIR/.env`, then
  `docker compose up -d` (with `--profile typed` for the broker). Not run here.
- **Mask or block.** The same line with `mask` or `block`. Mask rewrites personal
  data before it leaves the box; block refuses a call that carries it. Turn
  either on only after reading what it does to your agents' traffic.
- **The seeded policy is written only when `policy.yaml` is absent.** An existing
  box keeps its own file, and does not get the rehearsal policy.

## Measured

- `./scripts/pii-is-shadow.sh` on the tree this release is built from: `OK`, exit
  0. Its resolved-configuration check, `docker compose --profile typed config`,
  reads `shadow shadow` on a box that sets nothing, `off off` when `.env` sets
  `off`, and `block block` when it sets `block`.

## Not proven

- No `install.sh` run on a box with this release, and no live stack: a running
  gateway or broker recording a finding on a real call, mask or block against a
  real provider, and Wardryx refusing a tool outside `lookup_order_status` for the
  rehearsal identity. The `allow_tool` behaviour is the one described in the
  v1.1.30 notes, not one observed here.
- The gateway's shadow finding is not written to the bus or to a trace row. A
  finding that must be queryable later needs a TokenFuse change, not this launcher.
