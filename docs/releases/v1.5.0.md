# stack-single 1.5.0

Wave 3 of the 2026-10-17 agent-security review, closed for stack-single: protections the product now gives by default, the record plane signed through keyryx with its root pinned at install, and the released 1.5.0 digests of the upstream images. Each change has a gate, teeth cases and a feature file in this release.

## Upgrade first


1. Re-run `./install.sh` on each box, as for 1.4.0. Items 2 to 9 act on that run by themselves, except where a step below says otherwise.

2. **A box installed on 1.3.1 printed its console password into its install log, so change that password.** The 1.3.1 closing report printed it. A later install does not change an existing console operator, so the old password still works until you change it. Change it, then clear the install log that holds it. From the stack directory (`/opt/agent-stack` unless you set `STACK_DIR`):

   ```sh
   cd /opt/agent-stack
   read -r -s -p 'new console password (12 characters or more): ' PW && echo
   printf '%s\n' "$PW" | sudo docker compose exec -T console /usr/local/bin/genaryx-web set-password --username ops
   unset PW
   sudo docker compose restart console
   ```

   The username is `ops` unless you set `CONSOLE_USER`. The password is read from standard input, so it is not in the process list, and it is not on the command line. The console refuses a password under 12 characters. A console that is already running keeps the old password until it restarts, which is why the last line restarts it. Then sign in with the new password. The command is the one in genaryx's `set-password` path (genaryx `v1.1.45`, the version this stack pins). It was read from that source, not run on a live box for this note.

   A box installed from this release keeps its first password in `STACK_DIR/console-password` (mode 0600), and the closing report names that file and the one command that reads it. Delete that file once you have saved the password.

3. **With `TYPED_RISK_SIGNAL=1`,** the run writes the managed rule `typed-risk-hold-when-absent` into `policy.yaml` and restarts wardryx, which reads that file at start. From then on a tool call with no risk signal is held for a person, and so is one the classifier marks `destructive`, `external_send` or `financial` at 0.8 or more. That is the rule stack-up seeds. Other classes, or other thresholds, are your own `hold_if_signal` rule (README).

4. **vouchryx signs with the key keyryx certifies, by default.** The run takes the delegation root pin from the keyryx on the box and starts vouchryx on the certified key. Verifiers take the new key from the served key set. A box that wants the file key sets `VOUCHRYX_SIGNER=file` in `.env` before the run. To move the pin to a root keyryx now serves, follow the re-pin steps in the README ("Re-pinning keyryx's delegation root, on purpose"). This launcher sets no keyryx admin key, so a root cannot be rotated from this stack yet.

5. **CostCrew's runner spends only through the gateway, under a ceiling, and only when a person starts it.** The add-on's console could never spend, and its runner (`costcrew-run`) was not wired at all. Nothing changes until you ask. Two things follow from the upgrade, and both are yours to choose. First, the run adds the crew's client key `GATEWAY_COSTCREW_KEY` to `.env` and to the identity map, bound to `agent://<domain>/costcrew/*` in unit `costcrew`. The gateway accepts it from then on, and no service presents it until the runner is started. Second, `COSTCREW_CEILING` is written to `.env`, and it is `0` unless you set it: with `0` a runner run spends nothing, and the crew's key is not kept. The key is minted only while the ceiling is above 0, and a run at 0 removes it from the gateway's keys, so no unused credential is accepted. To allow spending, set `COSTCREW_CEILING` (a decimal, such as `25.00`), run `./install.sh` again, turn cadence on at the console's `/cadence` page, and start the runner with `docker compose --profile finops --profile crew run --rm costcrew-run`. Nothing schedules it here. Its runs are recorded in the costcrew store, not on the bus, because the bus stream has one writer.

6. **wardryx 2.4.0, and the console's approver key (CLAUDE.md invariant 58).** The console is now genaryx-console v1.6.0, which prints its approver key set, so the installer's probe turns approver statements on for this run: a console without an enrolled passkey cannot sign one, so its approvals are refused, and the passkey is enrolled first. Before you upgrade a box that sets an agent-token issuer (the default), confirm that the gateway and the MCP broker send a fresh DPoP proof with each `/v1/decide` call. wardryx 2.4.0 refuses a proof it has already seen within its window with `403 agent_token_proof_invalid`, and one agent request that causes two decisions must send two proofs. `WARDRYX_ALLOW_KEY_APPROVALS` is never set.

7. **The record seal signs through keyryx, reads the witness's attestations, and pins custody's root (CLAUDE.md invariants 59 and 60).** A run mints the seal's credential `keyryx/record-seal.key` (mode 0400, read only by the seal) and gives keyryx its digest. The seal reads the keyryx witness's attestations through a read-only `attestations` folder of its own, and nothing else of the witness's. At install it pins the kid of keyryx's `trailryx-root` key set, which must hold exactly one ES384 key; the pin is written to `.env` once and kept on every later run. If keyryx holds no ES384 key, or two, the run stops before anything starts for the record seal and says why. A rotation is done on purpose, as the README's "Rotating the record root" describes.

8. **The released 1.5.0 pins (CLAUDE.md invariant 61).** keyryx v0.1.2, trailryx-node v1.5.0, tokenfuse and its control plane v1.20.0, and genaryx-console v1.6.0 are pinned by digest. Each digest's cosign `.sig` tag was on the registry when this release was cut. The installer's own signature check runs on every pull of a `ghcr.io/taipanbox` image, as before. Nothing else needs doing: a re-run restarts a service whose image digest changed.

9. **Tokenfuse's two origin lists name every address the gateway and the broker are reached at (TODO(D13) is closed).** `TOKENFUSE_DELEGATION_ORIGINS` (the gateway) defaults to `http://tokenfuse-gateway:4100` and `http://${GATEWAY_BIND}:4100`; `TOKENFUSE_MCP_PROOF_ORIGINS` (the broker) defaults to `http://tokenfuse-mcp-broker:4200` and `http://${GATEWAY_BIND}:4200`. A box bound to `0.0.0.0` that is reached at its LAN address must list that origin in `.env` (comma separated, replacing the default), or calls at that address are refused.

## What changed

- **The record seal pins custody's trailryx-root kid at install** (CLAUDE.md invariant 60). The pin is `TRAILRYX_KEYRYX_KID` in `.env`, read once from keyryx's `/v1/jwks/trailryx-root`, and it refuses a set without exactly one ES384 key.
- **The record seal reads the witness's attestations through a read-only folder** (invariant 59, amended). `TRAILRYX_WITNESS_ATTESTATIONS` is set; the `TODO(keyryx-attest-mode)` is closed.
- **The 1.5.0 wave is pinned by digest** (invariant 61): keyryx v0.1.2, trailryx-node v1.5.0, tokenfuse and its control plane v1.20.0, genaryx-console v1.6.0 (which carries `approver-jwks`, so approver statements are on for this pin).
- **The gateway and the broker name each origin they are reached at** (invariant 61). `TODO(D13)` is closed.

## NOT proven

- **A keyryx root cannot be rotated from this stack.** The launcher never sets `KEYRYX_ADMIN_KEYS`, so keyryx's rotate and revoke routes refuse every call on a box it installed. A rotation needs that variable, which is not wired yet. The README's rotation steps for the record root cover only the pin, not keyryx's own root.
- **Nothing signed by the record seal has been verified live.** The seal's keyryx path, its bearer credential over HTTP, the witness's attestations, and the seal's read of them (`read --pack` with `TRAILRYX_WITNESS_ATTESTATIONS` set) were read from source and are checked by static gates, not run on a box.
- **The root pin on a live custody is assumed, not measured.** The gate uses stub key sets. It assumes keyryx creates the `trailryx-root` key set at its first start. A custody that does not serve it stops the install with the fetch error; the installer does not fall back to a guess.
- **Approver statements are on by the probe, not run.** The probe finds `approver-jwks` in v1.6.0; wardryx 2.4.0 accepting a statement from the console live, and the passkey requirement, were not measured.
- **Single-use DPoP proofs are not checked against the gateway and the broker.** The upgrade note asks you to confirm they send a fresh proof per decision before you upgrade a box with an agent-token issuer.
- **The origin lists have not been exercised on a live stack.** No request was measured at any address; a box bound to `0.0.0.0` and reached at its LAN address is refused until that origin is listed.
- **The 1.5.0 digests were not run on a live stack.** The installer's cosign check on each pull was not run here, and CI's install legs were not run here.
- **tokenfuse-control-plane v1.20.0 is pinned with the gateway, not measured by itself.**
- **The CostCrew runner has not spent money.** Its wiring was read and gated, not run against a model provider.
- **The console password change procedure was not run.** It was read from genaryx's source at the release that v1.1.45 pins.
