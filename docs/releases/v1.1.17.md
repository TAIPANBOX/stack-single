## What changes on an installed box

- **A run's budget is capped.** The gateway clamps the budget a caller declares
  for one run (`x-fuse-budget-usd`, a policy default or its built-in default) to
  `RUN_BUDGET_CEILING_USD`, 5.00 USD unless you set it. 5.00 is tokenfuse's own
  default run budget, so an ordinary run is unchanged and only a larger declared
  budget is lowered; a Cloud budget is never clamped. A clamped answer carries
  `x-fuse-budget-clamped`. It bounds one run, not an agent.
- **A chain verifier runs by default.** `agent-conform watch-dir` re-checks the
  hash chain of every stream on the bus every five minutes and writes
  `chain_broken` (high) to its own stream, `agent-conform.ndjson`, where the
  notifier already reads. It runs as its own account, outside the bus group, so
  it can write that one file and nothing else on the bus. The mail for a break
  names the agent and the kind, not the stream or the line (those are in the
  verifier's log).
- **Stream files are held to their source.** heraldyx v0.3.0 and idryx v1.1.0
  refuse a line whose `source` the file may not carry. Every file this launcher
  writes already matches (`<source>.ndjson`, plus `tokenfuse-cloud.ndjson` and
  `tokenfuse-mcp.ndjson` carrying `tokenfuse`), so no stream was renamed and
  `HERALDYX_STREAMS` and `IDRYX_STREAMS` stay unset. If you added a file of your
  own to the bus directory, check heraldyx's first start-up log for a line about
  a refused or undeclared file.
- **vouchryx's public revocation list no longer carries who revoked a token or
  why** (the operator's record still does). The gateway reads neither field.

## New and opt-in

- `TYPED_RISK_SIGNAL=1` (typed answers on; refused otherwise; off by default)
  starts `typryx wardryx-proxy` in front of wardryx and points only the MCP
  broker's policy client at it, so a tool call carries typryx's
  `action.risk_class` to wardryx, where a `hold_if_signal` rule you write can
  hold it for a person. Nothing seeds that rule. Turning it on makes the broker
  a policy enforcement point (it was not one here): every tool call is decided
  under your `policy.yaml`, a call with no `x-fuse-agent-id` is refused, and a
  call is refused if wardryx or the proxy cannot answer. `TYPED_RISK_SIGNAL=0`
  turns it off. See the README section "A risk signal on tool calls".

## Upgrade

Re-run `install.sh` (or `git pull` and `docker compose up -d`). The installer
adds nothing to `.env` for any of this unless you set a variable: the ceiling
defaults in compose, the verifier needs no setting, the signal is off. The
`events` volume gains `agent-conform.ndjson`, a new `conformstate` volume
appears, and a `risk-signal` network is created (wardryx joins it, nothing else
unless the typed risk signal is on). A box on `tokenfuse` v1.4.1 whose `TOKENFUSE_MODE` is anything but
`shadow`, `warn` or `enforce` would now refuse to start; this launcher sets
`enforce`.

## Not run

`install.sh` on Debian was not run by hand for this release; CI runs it twice,
default and delegation and with the typed risk signal. No real model backend
was asked: the signal was measured on the stub only. A `chain_broken` was
produced by flipping one byte of a stream on a scratch bus and was detected,
written and mailed (to a file) with the neutral wording above; a break on a
long-running box was not waited for. The clamp was measured against a local
stub standing in for the provider, never a real one.
