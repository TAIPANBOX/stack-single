# stack-single 1.10.0

A minor release that turns on the argument preview. The person deciding a held tool call in the console now sees the call's arguments, built by wardryx from the bytes the approval is bound to, with secrets and personal data hidden by fixed rules, and sealed so that only the console can read them. wardryx moves to v2.7.0 and the console to `genaryx-console:v1.12.0`, the first image that opens the preview, and the installer makes the console's preview key once.

It also takes the doors off the guests network. A container of another project on the box now shares a network with nothing of the stack but a proxy that holds no key: guest-door, which forwards a guest's routes to vouchryx, the gateway and the MCP broker, and guest-callback, which brings a call from the stack back to a guest, for callers on `core` only.

## Upgrade first

1. **Run the installer.** Before the stack starts it makes the preview key with the pinned console image (`genaryx-web preview-key`, ML-KEM-768 with X25519): `preview/preview.key`, mode 0400, owned by the console's uid, in a directory root's with the console's group, mode 0710, mounted read only into the console alone and never printed. The public half is kept at `preview-public/recipient` and set as `WARDRYX_PREVIEW_RECIPIENT`. A re-run keeps both. The rollback index stays 1.
2. **If only one of the two files is there, the installer stops** and starts nothing, because a recipient the key does not match would seal previews nobody can open. Remove the one that is there and run it again.
3. **A `CONSOLE_IMAGE` you named yourself** that cannot make the key turns the preview off, says so, and drops `WARDRYX_PREVIEW_RECIPIENT`, so wardryx keeps deciding as before for that console. The pinned image always makes it; if it does not, the install stops.
4. **What changes for a person approving.** A sealed hold shows "Show arguments", and a grant needs it opened first; a denial does not. A hold with no preview (no arguments, or arguments the enforcement point truncated) is granted with "Grant unseen", and the record says so. With a database, wardryx creates one new table, `approval_previews`, at start; it holds ciphertext only, until the hold is decided or 24 hours pass.
5. **A box with guests (a container of another project on `agent-stack_guests`) changes nothing for most of them.** vouchryx, the gateway and the MCP broker leave `agent-stack_guests`; guest-door takes their three names there, so a guest calls them as before, on the routes a guest uses: from vouchryx a token, its key set and metadata, the revocation list, and a revocation or its lift under a scoped key; from the gateway `/v1/messages` and `/v1/chat/completions`; from the broker `/mcp`; and each door's `/healthz`. Any other route, an administrative one of the gateway among them, now gets guest-door's own 404. A guest that is called back by a service of the stack (the broker calling a lab's relay as a tool upstream) needs three things before this run: a line in `guest-callbacks.txt` beside `compose.yaml` (`<container> <name>:<port>`, the container also in `guests.txt`), the guest joined to `agent-stack_callbacks` (which this release creates, so after the run), and the caller pointed at `http://guest-callback:<port>/...` instead of the guest's name. A guest that checks its caller's address (a relay that answers only the broker) now sees guest-callback's. A line that is not one call back stops the install before anything starts. A host process that read vouchryx's address on `agent-stack_guests` reads it on `agent-stack_core`.
6. **Going back to 1.9.0 needs nothing special.** The rollback index stays 1. 1.9.0 pins wardryx v2.6.2 and console v1.8.8, which neither seal nor open a preview; holds sealed before the rollback are decided without it. The key files and the table stay on the box, unused. It puts the doors back on `agent-stack_guests`; the `callbacks` network, guest-door's directory and `guest-callbacks.txt` stay, unused, and 1.9.0's `status` calls a guest on `agent-stack_callbacks` an unknown container.

## What is new

- **The preview key** (CLAUDE.md invariant 78): `preview_key_apply` in `install.sh`, `GENARYX_PREVIEW_KEY_FILE` and the `./preview` mount on the console, `WARDRYX_PREVIEW_RECIPIENT` on wardryx. Held by `scripts/preview-key-is-wired.sh`, which runs the block in a scratch box under umask 077 and 022 over a fresh box, a re-run, a half pair, a pinned console that cannot make the key, an operator's older console, a recipient outside base64url, and a link the container leaves in place of the key, with eighteen teeth cases and `features/the-console-reads-a-held-calls-arguments.feature`.
- **No door shares a network with a guest** (CLAUDE.md invariant 77, rewritten; #191). In 1.9.0 the doors sat on `agent-stack_guests` beside the guests, and Docker answers a name from every network a container is on, internal ones in name order, so a guest that took a name could be handed a call meant for the stack wherever that name did not answer first on a network sorting before `guests`: with the typed risk signal on, the broker asks every tool call's policy question of `typryx-wardryx-proxy`, which lives on `risk-signal` alone. guest-door (`guest-door/Caddyfile`) and guest-callback (its routes written by the installer from `guest-callbacks.txt` and core's subnets) run the image `caddy` runs, as nobody, with no environment, no published port, no admin endpoint and no mount but their own configuration. `status` reads `guest-callbacks.txt` as it reads `guests.txt`, fails a guest that answers on `agent-stack_callbacks` to another guest's call-back name, and compares guest-callback's routes with the file and core's subnets. Every install and `status` probe what a guest sees: no door on `agent-stack_guests`, the gateway's `/healthz` through guest-door, its `/v1/runs` refused by guest-door. Held by `scripts/guest-door-routes.sh` (new), `scripts/network-membership.sh`, twelve new cases of `scripts/status-reads-what-runs.sh`, their teeth cases and `features/a-guest-reaches-the-doors-and-nothing-else.feature`.
- **The pins**: wardryx v2.7.0 and genaryx-console v1.12.0, in every place either is pinned. The gates that name a pin (`images-are-verified.sh`, `approver-key-is-wired.sh` and the pin cases of `gates-have-teeth.sh`) read the new ones.

## Evidence

- CI on the release head: every install leg, `browser`, `upgrade` and `upgrade-tool-hold`, on a real Docker with the pinned console making the key. On the default leg a real guest called back answers a call from `core` through guest-callback and refuses one from `agent-stack_callbacks` with 403, and on every leg an alias a guest takes on `agent-stack_guests` resolves for no door.
- The guests' gates were run red first on the tree before #191: `guest-door-routes.sh` measures nothing there, `network-membership.sh` finds the doors on `guests` and no `callbacks`, and the new `status-reads-what-runs.sh` cases fail against 1.9.0's `install.sh`.
- Each new teeth case was run against the tree with its fault planted and failed for the reason it names.
