# stack-single 1.7.1

The console can turn a held tool call into a standing grant from its approvals inbox. The three services a certified key hangs on, `init-volumes`, `keyryx` and `vouchryx`, take the container baseline now that keyryx v0.1.4 retires vouchryx's oldest key at the bound instead of refusing the new one. wardryx 2.6.1 puts on the bus only the types the event registry lists for it. The browser keeps Chrome's sandbox under a seccomp profile of its own, and the installer measures the AppArmor line on each host.

## Upgrade first

1. **`init-volumes`, `keyryx`, `keyryx-witness` and `vouchryx` are recreated, once, and vouchryx asks custody for a new key.** vouchryx keeps its working key in memory, so a start costs a key, and custody keeps at most four live. On 1.7.0 a start at that bound got no key until the oldest aged out, up to three days (G3.11). keyryx v0.1.4 retires vouchryx's oldest key instead, once the next key has been signing for ten minutes, the name's overlap here, so no token the old key signed is still alive. A box whose keys are older than that, which is any box that has not just restarted vouchryx several times, gets its key at once, and vouchryx serves after the publish-ahead, two minutes. A burst of restarts inside ten minutes is refused at first, as before, and vouchryx asks again every five minutes. A second run recreates nothing and spends no key.

   Measured on Compose 2.26.1 with custody already at the bound: one `up` recreated the three in two seconds, keyryx v0.1.4 retired vouchryx's oldest key at its first request, and vouchryx served again 124 seconds later. `GET /v1/keys` read four live keys before and four live after, the oldest `retired`. The second `up` recreated nothing and the count stayed.

2. **wardryx is recreated with 2.6.1.** It decides as 2.6.0 did, with no schema step. On a Compose below 2.35 it takes `tokenfuse-gateway` and `console` with it, and `console` takes `caddy`; calls through a door stop while they restart. The console, `verdryx-drift` and `verdryx-slo` move to the console image v1.8.8 and are recreated too. "Always allow" asks for a passkey of an admin, as a grant asks one of an approver, so a console with no passkey enrolled shows the button and cannot complete it. Two facts 2.6.0 wrote onto the shared bus as `policy_loaded` and `approval_queue_full`, which the registry does not list for wardryx, are now lines in its own log: `wardryx: policy set loaded ... no_grant_floors=[...]` at each start, and `wardryx: an agent reached its pending cap` once per agent. A hold past the cap is still recorded as `approval_requested` with `queue_full: true`. The installer's check `wardryx loaded the tool hold` and the line `status` prints read the start line from `docker logs`; a `policy_loaded` record 2.6.0 left on the bus names an older start, and nothing reads it.

3. **On a box that runs the browser, `scopyx-browser` is recreated too** (#175), with `seccomp/chromium-v1.json` in place of `seccomp:unconfined`, and `.env` gains `SCOPYX_BROWSER_APPARMOR`: `unconfined` on Debian 13, `docker-default` on Ubuntu 24.04, whichever the installer's throwaway shows Chrome's sandbox starts under. A box without the `egress` or `browser` profile has no browser, and nothing changes there.

4. **Going back to 1.7.0 needs nothing special.** The rollback index stays 1: no older tree became unsafe. 1.7.0 recreates the three again, and keyryx v0.1.3 opens custody's data directory with its `retired/` records, raises no alarm, and publishes a retired key again until its natural end. On a box at the bound that puts the 1.7.0 behaviour back: a start of vouchryx can wait until the oldest key ages out. wardryx 2.6.0 writes `policy_loaded` on the bus again, which 1.7.0's check reads.

## What is new

- **Always allow, from the approvals inbox** (genaryx#152, in the console v1.8.8). A tool call held because nothing grants the tool gets "Always allow" beside Grant and Deny. It writes the policy `./install.sh agent-allow` writes, through `PUT /v1/policies`, adding to what the agent already holds, so `./install.sh agent-deny` takes it back. It takes the `admin` role and the passkey ceremony a grant has, bound to that hold. An agent id with no trust domain gets no button and a line saying why, and a hold that came with a static key is granted one. The call on the row still waits for its own answer; the agent's next call passes. The console's engines are wardryx 2.6.1 and tokenfuse 1.23.0, the stack's own.
- **The three a certified key hangs on carry the baseline** (CLAUDE.md invariant 72). `keyryx` and `vouchryx` merge the anchor with a process limit of their own, 128 and 256. `init-volumes` merges it too, stays root because re-owning every volume is its whole job, keeps a limit of 32 processes, and takes back three capabilities, each measured by taking it out: `CHOWN`, `DAC_OVERRIDE` to enter keyryx's 0700 directory, and `FOWNER` to chmod what other uids own. `hardening-exceptions.json` loses its four `until: G3.11` lines for them and gains the one for those three capabilities.
- **The gate holds the custody under them.** `scripts/containers-carry-the-baseline.sh` fails on any exception that still waits on G3.11, on any baseline exception for the three, and on a keyryx pinned below v0.1.4, because changing the three under an older custody would put the bound back under vouchryx.
- **caddy's root line names what it waits on now.** It waited on G3.11 because its volumes are root's and re-owning them is a change to `init-volumes`. Its binary also takes `NET_BIND_SERVICE` from a file capability, so a uid of its own is a change of its own, and the line says so.
- **The browser keeps both sandboxes, on either supported host** (#175, CLAUDE.md invariant 71). `seccomp/chromium-v1.json` is Docker's default profile plus three rules, each measured by taking it out: `chroot`, `clone` into a user, pid and net namespace and no other, and `unshare` into a user namespace and nothing else. A change to the profile is a new file, because Compose hashes the line that names the file and never its contents, and the gate pins the digest to the name. `install.sh` measures the AppArmor line with a throwaway under the browser's own user, filter and capabilities, `docker-default` first. The piped install fetches the profile beside `compose.yaml`, and `status` holds a running browser to the profile the file names.
- **A refused chown stops `init-volumes` and `costcrew-init`.** Both run under `sh -e`, and `sh -e` does not stop on a command before `&&`, so `chown A && chmod B` with a refused chown went on and ended `volumes ready`, exit 0, the volume left with the wrong uid. While `init-volumes` held every capability that never happened; with three of them it can. Each chown is now its own command, and `scripts/volumes-are-reowned.sh` makes each one fail in turn and requires the one-shot to stop every time.
- **`wardryx loaded the tool hold` reads wardryx's own log.** wardryx 2.6.1 says the floors it loaded in its start line and no longer on the bus, so the check and `status` read `docker logs` of the running wardryx, the last start line, and never a record on the bus.
- **CI's `upgrade` leg says what holds now.** On Compose 2.26.1 it installs the previous tag and upgrades: custody holds between one and four live vouchryx keys afterwards, a second run recreates nothing, and the second run spends no key.

The README has the rest: [Every container starts with the least it needs](../../README.md#every-container-starts-with-the-least-it-needs) and the paragraph "A restart spends a key, and the bound holds" under the delegation plane.
