# stack-single 1.1.29

The gateway's agent firewall runs in `enforce` by default. Until this release it
ran in `shadow`, which records what it would refuse and refuses nothing. One
installer variable, `TOKENFUSE_FIREWALL`, moves it back to `shadow` or `off`.
The decision is recorded as invariant 27 in CLAUDE.md. No pin moves: TokenFuse
stays at `v1.11.0`.

## What changes

- **Every gateway starts with the firewall in enforce.** `compose.yaml` sets
  `TOKENFUSE_FIREWALL: ${TOKENFUSE_FIREWALL:-enforce}` on `tokenfuse-gateway`,
  the only gateway start in this launcher. The MCP broker, `focus-export` and
  the control plane are not gateways and do not read the switch.
- **One switch, validated.** `TOKENFUSE_FIREWALL` takes `enforce`, `shadow` or
  `off`, from the environment of `./install.sh` or from `.env`. `install.sh`
  refuses any other value before it installs a package or writes a file.
  TokenFuse runs its default on a value it does not know, and that default is
  shadow, so a misspelling would otherwise go unnoticed.
- **A gate for the default.** `scripts/firewall-is-enforce.sh` fails when a
  gateway defaults to shadow or off, when the setting is a literal or reads
  another variable, and when it finds no gateway at all. It runs in CI, in the
  pre-push hook and in the teeth harness.

## What enforce refuses that shadow did not

**Read this first.** A tool call named `run_shell`, `exec`, `bash`, `write_file`,
`db_write`, `deploy`, `send_email`, `http_post` or `send_message` (exact names,
case sensitive) is refused when the same run has earlier called a tool the
firewall treats as untrusted, and that includes every tool its source map does
not name at all (labelled `unclassified`). So an agent that calls any tool of
its own and later, in the same run, one of those nine names is refused. An
operator whose agents chain those names on purpose keeps
`TOKENFUSE_FIREWALL=shadow`, or gives the gateway a policy file
(`TOKENFUSE_FIREWALL_CONFIG`) that classifies their tools.

Shadow records a decision and lets the answer through. Enforce withholds the
answer. In enforce, the gateway refuses a model answer with HTTP 403 and
`taint_blocked` in three cases:

1. The run has read untrusted input (a web page, an email, a file, a source it
   does not classify, or a tool result that read like an instruction), and the
   model asks for exec, write or network egress.
2. The run holds a secret and the model asks for network egress. This is the
   anti-exfiltration floor, which enforce locks on.
3. A tool the request declares was read as poisoning (TokenFuse invariant 93, a
   `high` or `critical` finding). That labels the run `suspected_injection`, and
   the model then asks for exec, write or network egress.

## What does not change

- A run that never asks for one of the nine names above is answered as before,
  whatever else it called. The console's copilot is such a run: its seventeen
  tools only read or propose, so it is labelled `unclassified` and never refused.
- The budget, policy and identity checks are unchanged.
- The model call is recorded and billed as before. A refusal adds one
  `taint_blocked` record and no cost.
- `shadow` and `off` behave as they did in v1.1.28. Shadow still records
  `taint_raised` and `taint_shadow`.
- The MCP broker's configuration does not change. It is opt-in (`typed`
  profile), and where it runs, its taint decisions come from the gateway.

## Limits

- **Streamed answers.** Enforce judges the buffered answer. A tool use inside a
  streamed answer is not withheld in this release. This is a limit of TokenFuse
  `v1.11.0`, not a launcher setting.
- **Refusal and the client.** A withheld answer does not reach the client, so
  the client never receives that tool call. A client that asks
  `check-tool-call` before it runs a tool gets the decision in the response body.
- **Per run.** Labels belong to one run. A new run starts with none.

## Upgrading

- **An existing box runs enforce from its next `docker compose up`.** Its
  `.env` has no `TOKENFUSE_FIREWALL` line, so compose supplies `enforce`. The
  box does not keep shadow on its own.
- **To keep shadow,** set `TOKENFUSE_FIREWALL=shadow` in
  `/opt/agent-stack/.env`, then run `./install.sh` (which checks the value) or
  `docker compose up -d tokenfuse-gateway`.
- **Start-up log.** The gateway logs its firewall mode at start (`agent
  firewall`). This is read from TokenFuse's source and was not checked against
  a running gateway.

## Not proven

- Measured on a local test stack, not on a live deployment: stack-k8s's
  `evidence/closure-e2e` Docker Compose harness (gateway and control plane
  `v1.11.0`, console `v1.1.36`, heraldyx `v0.4.0`), shadow then enforce, on
  2026-10-13. The harness passed 44 of 44 in both modes. mockryx's twelve
  shipped scenarios against a provider stub answering 200 differed in exactly
  three, `injected-page`, `egress-after-untrusted-read` and
  `declared-tool-poisoning`: a gap in shadow, passed in enforce. A
  copilot-shaped request (a read tool in the history, then an answer naming
  `bash`) got 200 with a would-block header in shadow and `403 taint_blocked`
  in enforce. That stand is not this launcher's compose file.
- `install.sh` run with this change on a Debian or Ubuntu box, and a live model
  call under enforce.
- A withheld call observed at a running gateway, for each of the three cases
  above.
- The MCP broker's own taint decisions under enforce.
- Streamed answers under enforce (see Limits).
