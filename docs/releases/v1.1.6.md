# stack-single 1.1.6

The notifier moves to heraldyx 0.2.5 (heraldyx `docs/releases/v0.2.5.md`):
after the hourly mail ceiling, held alerts are summarised every ten minutes
(sooner for a burst of fifty) and a critical alert still goes out. On 1.1.5
the notifier fell silent after the twentieth mail of the hour, which the
2026-09-17 appliance run measured for 28 minutes.

The policy plane moves to wardryx 1.0.3 (wardryx#63): a readiness endpoint,
`GET /readyz`, pings the store under a 3 second timeout and answers whether
wardryx can actually serve, not only that its process is up. Diffing
`components.json` between the pinned 1.0.2 and this ref found no other
change: no env var added or removed, no default changed.

The two money-plane images move together to TokenFuse 1.0.4 (tokenfuse
`docs/releases/v1.0.4.md`): the gateway no longer follows a provider
redirect, so the caller's key and prompt cannot follow a 307 to another
host, and a `send` error after the connection existed is retained as an
unknown outcome instead of released. A deployment whose `TOKENFUSE_UPSTREAM`
relied on a redirect must point at the final address. Diffing
`components.json` between the pinned 1.0.3 and this ref found no change:
no env var added or removed.

## The pinned set

As in 1.1.5, with `heraldyx:v0.2.5` in place of v0.2.4, `wardryx:v1.0.3` in
place of v1.0.2, and `tokenfuse:v1.0.4` / `tokenfuse-control-plane:v1.0.4` in
place of v1.0.3.

## Limits

- SMTP delivery after the ceiling change is not measured on an appliance; the
  heraldyx release measured file delivery.
- No install or reboot was run on this pinned set. The earlier appliance run
  and this release's static gates do not prove it on a fresh box.
- wardryx's new `/readyz` is not wired into this launcher's own health check
  (`install.sh` section 8 still reads `/healthz`, both here and inside the
  compose network). Wiring it in is a follow-up, not part of a
  version-only re-pin.
