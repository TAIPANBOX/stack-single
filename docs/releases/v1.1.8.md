# stack-single 1.1.8

TokenFuse moves to 1.1.1, and the gateway's semantic cache is switched off
explicitly. Together they remove the gateway's throughput ceiling on this
box.

## What changed

- **`tokenfuse` and `tokenfuse-control-plane` are pinned at v1.1.1** (they
  were v1.0.4). TokenFuse 1.1.0 and 1.1.1 lie between; 1.1.0 adds features
  that are off unless configured, so a deployment that sets none of them
  behaves as before. 1.1.1 is the fix below.
- **`TOKENFUSE_CACHE: "off"` on the gateway (#68).** With the variable unset,
  TokenFuse up to 1.1.0 ran its semantic cache in shadow mode, which compared
  every call against everything it had stored under one lock. On a 4-core
  box that capped the gateway at about one core, slowed it the longer it
  ran, and at 50 agents and more made the policy check time out and refuse
  legitimate calls. A gate, `scripts/gateway-cache-is-off.sh`, fails if a
  gateway service loses the setting.

## Measured

On one 4-core Intel N150 box running this launcher's stack, 100 concurrent
agents against a mock upstream: 119 calls/s with 46% refused on TokenFuse
1.0.4, 1987 calls/s with none refused on 1.1.1's gateway code with the cache off. With the
published 1.1.1 image and a real provider (Anthropic, Claude Haiku 4.5, a
different prompt on every call), 20 and 50 agents made 3,331 calls in 60
seconds, every one answered 200, none refused, p50 about 0.6 s.

## Upgrade

Re-run `install.sh` on the box. Two images are pulled, the gateway's and
the control plane's; `.env` is left as it is.

## Not in this release, said plainly

- A full `install.sh` run with this pinned set was not made on a fresh box.
  The measurements above ran the 1.1.1 gateway inside an existing install of
  this launcher, with the rest of the stack unchanged.
- An operator who turns the cache back on with `TOKENFUSE_CACHE=shadow` pays
  for it under varied traffic: a new prompt is still compared against every
  stored entry (TAIPANBOX/tokenfuse#329).
