# stack-single 1.0.0

Deployment two of three of the TAIPANBOX stack: one Debian or Ubuntu box, one
installer, one Compose file. The first release of this repository. A stack
release is a pinned set with a date, nothing more: this one pins the planes
released at 1.0.0 on 2026-09-13 and names the ones that are not there yet.

## The pinned set

| Service | Image | Release |
|---|---|---|
| policy plane | `wardryx:v1.0.0` | 1.0.0 |
| identity plane, `idryx-detect` | `idryx:v1.0.0` | 1.0.0 |
| web-egress plane (`--profile egress`, `egress-browser`) | `scopyx:v1.0.0`, `scopyx:v1.0.0-chromium` | 1.0.0 |

`components.json` carries the same list and `scripts/manifest-is-true.sh`
holds it against `compose.yaml` on every push; estate-gates C20 holds the
README's lines against the tags that exist.

## Proven, by the 1.0 proving run (estate-gates `PROVEN.md`, "The 1.0 proving run")

- **INS-2 on this set, R1 GCP, 2026-09-13.** The README one-liner on two fresh
  `e2-standard-2` boxes: **109 s** each, exit 0, **22 checks ok, 0 fail**,
  8 images pulled, 0 built; the same installer again on the same box: **35 s**,
  22 ok, the container set byte-identical before and after.
- **The four 1.0.0 planes on the box.** `scopyx` started from its profile
  fetched a page through the MCP door and wardryx wrote the `policy_allow`
  with the recorded question; `record-seal` ran its first pass and said,
  loudly, that there was nothing to seal yet; `wardryx v1.0.0`, `idryx v1.0.0`,
  `trailryx-verify 1.0.0` from inside the containers.
- **INS-2, INS-3, R1 on the 0.x pins, the same morning.** 112 s, 33 s
  idempotent, 116 s on a second fresh box on x86_64; 83 s on arm64
  (`t2a-standard-2`), every image resolved `linux/arm64`.
- **UPG-1 and UPG-5, R1.** A gateway image moved in `.env`: `docker compose
  up -d` converged in 7 s recreating only the gateway; volumes and the policy
  store untouched; the trace written by the old gateway read by the new one.
- **INS-7, POL-3, FAIL-2, INT-5, REC-3, UPG-3, FAIL-5, R1.** The README
  commands of qryx, idryx and trailryx on the box; scopyx's five gates with
  the stand's wardryx; the gateway fail-closed and scopyx `deny_policy_unreachable`
  with the policy plane killed; the record plane's erasure and the full disk.

## What the installer promises

- It fails before doing half the job: every refusal precedes the first side
  effect, every fetch and start carries `|| die`.
- The stack comes up closed: the gateway on `127.0.0.1` unless `GATEWAY_BIND`
  says otherwise, the console on loopback, the tunnel the only public port.
- It verifies its own bring-up: 22 checks at the end, five of which must
  FAIL to pass (an unknown key, a viewer key writing policy, the planes not
  reachable from the host); the exit code is the number of failed checks.
- The second run is the real test: re-running it on an installed box changes
  nothing it does not have to.
- A profile's image is pulled by `WITH_EGRESS=1`, `WITH_BROWSER=1`,
  `WITH_RECORD=1`; the operator starts it, since egress is the widest grant the
  stack has.

## Upgrade note, an installed box to 1.0.0

Run the installer again. `.env` is never rewritten, only added to; `compose`
recreates only the services whose image moved (UPG-5: 7 s); the policy store
and every volume stay. Two things the moved planes bring: wardryx approval
tokens are single-use by default from 1.0.0 (`WARDRYX_APPROVAL_SINGLE_USE=false`
restores the 0.1.0 reuse; a token minted by 0.1.0 still verifies), and the
wardryx and idryx schemas migrate themselves on connect (UPG-2, wardryx 0.1.0
to 1.0.0 on Postgres, the policy and the pending holds restored).

## Not in this release, said plainly

- The money plane is 0.5.1; its 1.0 follows in the next wave with a launcher
  minor.
- The console and the tunnel images are 0.1.2; a stack-k8s tag publishes the
  console composition at its own version, and this launcher moves to it after
  a run proves it.
- No arm64 run on the 1.0 set tonight (the morning's arm64 run was on the 0.x
  pins; every 1.0.0 image is a linux/amd64 and linux/arm64 manifest list).
- The browser egress variant was pulled by nobody in the proving run.
- Notifications (heraldyx) need `ALERT_TO` and an SMTP host the box can reach;
  the proving run gave it neither.
